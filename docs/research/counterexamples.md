# Research: Counterexamples & Invariant Attacks

> **Цель**: Атаковать собственную концепцию контрпримерами до начала реализации. Если система переживает проверку «а что если…» — инварианты найдены верно. Если какая-то часть разрушает всё — она либо слишком фундаментальна (и должна быть явно признана инвариантом), либо слишком пронизывает архитектуру (и требует переработки).

---

## Контрпример 1: Может ли модель работать вообще без браузера?

**Проверка**: Убираем Web Runtime из кластера полностью. Остаются ядро, System Bus, Python Runtime, Vault, Memory.

**Ответ**: **Да.** Ядро не знает про браузер — оно знает только про узлы, шину и граф возможностей. Планировщик просто не сможет разрешить интенты, требующие `web.dom.*` (получит структурированное объяснение «возможность недоступна»), а все остальные задачи (код, файлы, боты, хранилище) продолжат работать.

**Вывод**: Браузер — **НЕ инвариант**. Он обычный userland-рантайм. ✅ Инвариант подтверждён.

---

## Контрпример 2: Может ли система работать только с Python Runtime?

**Проверка**: В кластере один узел с Python Runtime (например, планшет). Никаких браузеров, Docker, почты.

**Ответ**: **Да.** Система вырождается в классический «LLM + Python-исполнитель» (ровно то, что уже работает в Dirom), но с сохранением каркаса: шина, узел, граф возможностей, планировщик. Всё лишнее просто не зарегистрировано.

**Вывод**: Ядро не зависит от типов рантаймов. ✅ Инвариант подтверждён.

---

## Контрпример 3: Что если в системе вообще нет LLM, а Planner — обычный алгоритм?

**Проверка**: Убираем LLM. Планировщик — детерминированный алгоритм (например, декомпозиция по заготовленным шаблонам задач).

**Ответ**: **Да.** Планировщик — userland-сервис на шине. Он не обязан быть LLM. Детерминированный планировщик может исполнять типовые конвейеры («зарегистрируйся → подтверди почту → сохрани секрет»). LLM — это просто один из возможных планировщиков, подключаемых на ту же шину.

**Вывод**: LLM — **НЕ инвариант**. Ядро не знает о существовании моделей. ✅ Инвариант подтверждён.

---

## Контрпример 4: Можно ли заменить Capability Engine, не разрушив остальные документы?

**Проверка**: Заменяем реализацию вывода возможностей (например, графовый инференс → табличный классификатор или внешний сервис).

**Ответ**: **Частично.** Контракт «из API → Behavior → Capability» является инвариантом: планировщик и рантаймы зависят от него. Но конкретная реализация вывода (алгоритм, движок, библиотека) — заменяема, пока сохраняет контракт.

**Вывод**: Лестница **API → Behavior → Capability → Intent** — инвариант. Конкретная реализация Capability Engine — заменяема. ✅/⚠️ Частично подтверждён: слой абстракции фундаментален, движок — нет.

---

## Контрпример 5: Работает ли система с нуля узлов?

**Проверка**: Кластер пуст, ни один рантайм не подключён.

**Ответ**: **Да.** Ядро живо: шина работает, Node Manager ждёт подключений, планировщик честно отвечает «ни одна возможность недоступна». Система — это каркас, а не приложение.

**Вывод**: Ядро самодостаточно. ✅ Инвариант подтверждён.
