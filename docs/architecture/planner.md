# Architecture RFC: Planner (Intent Resolution Service)

## 1. Что это (What it is)
**Planner (Планировщик)** — это userland-сервис, который превращает намерения (Intents) агента в последовательности вызовов методов рантаймов через System Bus. Планировщик **не является частью ядра** и может быть заменён любой другой реализацией (другая LLM, классический алгоритм, гибрид).

Поток работы:

```text
Intent: "Опубликуй видео на YouTube"
        │
        ▼
Planner: "Нужна возможность video.publish"
        │
        ▼
Capability Engine: "Граф: video.read + browser.dom + vault.yt_tokens + mail.otp"
        │
        ▼
Node Manager: "video.read → node-main; browser.dom → node-browser; ..."
        │
        ▼
System Bus: исполнение шагов, сбор результата
```

## 2. Почему существует (Why it exists)
1. **Развязка мышления от исполнения**: LLM мыслит задачами («прочитай текст со страницы»), а не capability-именами (`dom.read`). Планировщик выполняет роль переводчика.
2. **Объяснимость (Explainability)**: Если задача невозможна, планировщик возвращает структурированное объяснение: *«Не хватает возможности browser.dom — Browser Runtime не подключён»*.
3. **Заменяемость**: Планировщик можно заменить целиком (новая модель, новая стратегия декомпозиции), не трогая ядро и рантаймы.

## 3. Что НЕ входит (What is NOT included)
- **НЕ является ядром**: Планировщик — один из многих сервисов на шине.
- **НЕ исполняет вызовы напрямую**: Все вызовы идут через System Bus и Capability Engine.
- **НЕ хранит долгосрочное состояние**: История и память — в Workspace Memory.

## 4. Открытые вопросы (Open Questions)
1. Как планировщик выбирает между узлами с одинаковыми возможностями (латенси, стоимость, надёжность, контекст)?
2. Нужен ли отдельный Reasoner для критических решений (страховки перед необратимыми действиями)?
3. Как планировщик взаимодействует с человеком для подтверждения опасных шагов (Human-in-the-loop)?
