# Architecture RFC: Cluster & Node Manager

## 1. Что это (What it is)
**Node Manager** — это подсистема ядра, управляющая жизненным циклом распределенных узлов (Node) кластера. Каждый узел представляет собой среду выполнения (например: ноутбук с Linux, планшет с Termux, вкладка Firefox с Tampermonkey, облачный VPS с Docker).

Каждый узел при подключении регистрирует:

```json
{
  "node_id": "node-browser-laptop",
  "node_type": "browser",
  "host": "laptop",
  "latency_ms": 4,
  "services": ["kasper-bridge-dom", "kasper-bridge-events"]
}
```

## 2. Почему существует (Why it exists)
**AgentOS Cluster** — это отражение реальной распределенности пользователя: агент уже физически живет на нескольких устройствах (ноутбук, планшет, VPS). Node Manager обеспечивает:

1. **Discovery**: Автоматическое обнаружение новых узлов и их сервисов.
2. **Health Monitoring**: Периодические heartbeat-проверки.
3. **Latency Awareness**: Планировщик получает информацию о задержке при выборе узла исполнения.
4. **Failover**: При отключении узла его возможности переходят в `UNAVAILABLE`, а планировщик перенаправляет задачи на живые узлы с аналогичными возможностями.

## 3. Что НЕ входит (What is NOT included)
- **НЕ является оркестратором контейнеров**: Управление контейнерами — задача `Docker Runtime`.
- **НЕ управляет балансировкой нагрузки на уровне приложений**: Распределение задач между узлами с одинаковыми возможностями — задача планировщика.
- **НЕ контролирует доступ и права на узлах**: Доступность прав решается на уровне самого рантайма.

## 4. Открытые вопросы (Open Questions)
1. Как обеспечивается безопасность подключения новых узлов (mTLS, общий секрет, challenge-response)?
2. Как обрабатывается ситуация, когда два узла объявляют одинаковые возможности с разными правами и контекстами (личный браузер vs изолированный браузер-песочница)?
3. Нужна ли репликация состояния ядра между несколькими главными узлами (HA-кластер)?
