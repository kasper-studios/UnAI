# ADR-0004: Одноразовые login-тулзы и управление сессиями воркспейсов

> Status: **Accepted** (2026-08-08).
> Decision: У каждого воркспейса, требующего авторизации, ровно одна
> `login`-тулза. Она **автоматически скрывается** из MCP-набора после первого
> успешного вызова с валидными данными и **автоматически возвращается** по
> фактическому признаку невалидности сессии (реальный 401/expired, не таймер
> и не догадка). Юзер всегда может принудительно сбросить сессию
> (`unai workspace reset-session <id>`), что пробуждает `login` поверх
> автоматики.

---

## 1. Что это (What it is)

Каждый воркспейс, которому нужна авторизация (Discord, Telegram, GitHub, Vault,
…), объявляет ровно одну тулзу `login`. Это **не постоянный инструмент**, а
состояние-зависимый:

- **сессия валидна** → `login` НЕ видна в MCP-тулсах агента. Агент работает
  через остальные тулзы воркспейса, не думая о входе;
- **сессия невалидна** (`none`/`invalid`) → `login` снова доступна агенту,
  и он может выполнить вход;
- **первый успешный login** → валидные данные сохранены, тулза снова скрыта.

Всё остальное в наборе тулов воркспейса не зависит от состояния входа.

## 2. Почему (Why it exists)

1. **Агент не должен переавторизовываться по своей воле.** Если сервис
   отдал 401 — это сигнал для ЛОГИНА, а не для фоновых копирований токенов.
2. **Автоматика экономит оверхеад**: агент не видит мёртвых тулов и не
   тратит токены/время на раздумья про авторизацию.
3. **Автоматика не гадит**: скрытие/появление логина основано только на
   **фактическом состоянии сессии**, а не на таймерах и предположениях.
   Это важно: эфемерный сетевой сбой — не повод прятать тулзы, а
   протухший токен — не повод молчать.
4. **Юзер всегда главнее автоматики**: ручной `reset-session` — «красная
   кнопка», которая сбрасывает любое состояние (смена аккаунта, утечка,
   желание перелогиниться). После неё `login` доступна даже если формально
   сессия была валидна.

## 3. Как это работает (механика)

Состояния сессии воркспейса:

```text
none → await_login → valid
        │              │
        └── invalid ───┘   (фактический 401 / expired / reset)
```

- `none` — воркспейс установлен, вход ещё ни разу не делался → `login` видна;
- `login` успешен → состояние `valid`, `login` скрыта;
- получили достоверный признак невалидности (401 от API, expired-токен) →
  состояние `invalid` → `login` видна снова;
- `unai workspace reset-session <id>` (юзер) → состояние `none`/`invalid` →
  `login` видна.

Где хранится состояние:

- **Состояние сессии** — в данных воркспейса (`~/.unai/data/<id>/`,
  например `session.json`), не в коде и не в `~/.unai/workspaces/<id>/`.
- **Что понимается под «валидными данными»** — решает сам воркспейс
  (токен/кука/пароль…), это его внутренний контракт. Ядро и CLI знают
  только три состояния: `none | valid | invalid`.

## 4. Какие есть НЕ (What is NOT)

- **НЕ** постоянная login-тулза «на случай» — только state-зависимая.
- **НЕ** автоматический перенос кук/токенов между воркспейсами. Агент сам
  решает, что и куда перенести (браузер собрал — пихнул в нужный воркспейс),
  без нашего авто-подхватывания.
- **НЕ** таймеры/эвристики «сессия наверное кончилась». Только фактическая
  инвалидация или ручной reset.
- **НЕ** `login`-механика для браузера как такового: браузерный воркспейс —
  это среда, а не сервис с API; его «аккаунты» — профиль юзера.

## 5. Открытые вопросы

1. Как CLI узнаёт про состояние сессии воркспейса для
   `unai workspace reset-session` — читает `~/.unai/data/<id>/session.json`
   напрямую или спрашивает воркспейс методом `session_status()`?
2. Нужен ли `session_status()` как обязательный метод SDK-класса, или
   достаточно опционального хука?
3. Показывать ли в `unai workspace ls` бейдж состояния (`none/valid/invalid`)?
